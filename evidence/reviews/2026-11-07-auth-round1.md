# Review: auth round 1 (P1), 2026-11-07

Reviewer: test-reviewer. Scope: `tests/{e2e,api,a11y,visual}/auth/*`, framework changes in `src/` (uncommitted, branch `feat/auth`), against `specs/auth.md`, `suite-conventions`, `flaky-triage`. Static review; visual not run (by design); run results taken from the 2026-11-07 log (33 passed, 12 failed, 14 skipped).

## Verdict: CHANGES REQUESTED

The suite is largely well built: IDs and titles trace to the plan, API tests assert status plus exact bodies, the fixmes assert the expected behaviour and nothing is weakened, and cleanup is guaranteed in teardown. Three items block the merge.

## Blocking

1. `tests/visual/auth/vr-03-register-errors.spec.ts:10-21`: the `first-name-error`, `last-name-error`, `country-error`, `postal_code-error`, `house_number-error`, `street-error`, `city-error`, `state-error`, `phone-error`, `email-error`, `dob-error` and `password-error` ids are recorded nowhere (not in `specs/auth.md` Verified facts, not in `toolshop-domain`; only `login-error` and `totp-error` are). CLAUDE.md rule 3 forbids unverified `data-test` ids, and the visual test cannot be validated locally. Fix: verify them in the browser, record them in the plan and the domain skill, or wait on the verified message text (`getByText(..., { exact: true })`, as TC-12 does).
2. `tests/e2e/auth/tc-02-customer-cannot-see-admin-content.spec.ts:13` (same pattern at `tc-01...:19`): `nav-admin-dashboard` `toBeHidden()` is asserted while the nav-menu dropdown is closed, so it passes even if the admin items are in the DOM. It can never fail as written. Fix: open `nav-menu` first (`customerPage.getByTestId('nav-menu').click()`) or drop the line. For TC-01, anonymous users have no nav-menu, so drop it.
3. Merge gate (CLAUDE.md rule 1, needs a green run): the last run has 12 reds (TC-02, TC-03, TC-05 x3, API-01/02/03), so the gate is not met. They are environmental (423 on the shared `customer@`), but see "Design risk" below: as written, the gate cannot be met reliably. Fix: decouple the tests from the lockable account (should-fix 1), then re-run all projects green and attach the run to the evidence log.

## Should fix

1. Design risk of the shared demo customer (TC-02, TC-03, TC-05, API-01, API-02, API-03 all log in as `customer@`; `customerPage` at `src/support/fixtures.ts:111`, `apiAs` in the same file). Any third party can lock it with 3 bad logins (423) and 6 test IDs x browsers go red with no product defect. The human rule says every user other than the demo accounts is synthetic. Fix: add a `syntheticCustomerPage` / `apiAs`-style fixture backed by `syntheticAccount` and use it for TC-02, TC-05, API-01 (customer branch), API-03 and API-02 (assert the synthetic email); keep exactly one demo-customer login (TC-03) as the canary. Also make a 423 fail loudly: `src/api/toolshop-client.ts:50` says "seeded account" with no status, so include `response.status()` and body in the message, and add the same to the `customerPage` URL wait. Triage is then immediate.
2. `tests/e2e/auth/tc-18...:14-18` and Q1: `test.fixme(true, ...)` and `test.skip(project...)` in the body run after fixtures. TC-18 (the only fixture-heavy one) registers a user and does an admin login + delete on all 3 browsers every run, for a test that never executes (3 registrations + 3 admin logins per run on the shared DB). Not acceptable long term. Fix: declare it as `test.fixme('TC-18 ...', { annotation: { type: 'fixme', description: '...' } }, async ...)` (no fixtures set up), and make the browser restriction declarative (`test.skip(({ browserName }) => browserName !== 'chromium', ...)` at describe level, or a project-level `testMatch`). Verify via trace that `syntheticAccount` setup steps are absent on firefox/webkit. The same declarative form is cheap and cleaner for TC-17, TC-19, API-17, A11Y-01, A11Y-02 (they only use `page`/`api`, so low cost today). TC-13's in-body skip (`tc-13...:14`) is acceptable: its fixtures are cheap (`cleanupUsers` with nothing registered), but the declarative form is still better.
3. `tests/e2e/auth/tc-18...:5-6, 27-29` (Q3): the filter is partly dead and unverified. Angular reports errors through `console.error` ("ERROR TypeError: ..." per `specs/coverage.md` CHPW-JSERR), so the `console` listener is the one that fires; the `pageerror` listener may also fire, giving duplicates (harmless). The qrcode exclusion compares `error.message` to the exact string `'qrdata is empty'`, but candidate #7 was seen as a console error, which cannot contain `TypeError`, so the exclusion never matches anything and is unverified. The plan says only pageerror is asserted and nothing is filtered. Fix: drop `KNOWN_QRCODE_MESSAGE`, keep both listeners unfiltered (or the exact TypeError text), and note in the test that the console path is the real signal. Also `expect(errors)` runs right after `fill`; if Angular rethrows asynchronously it can pass vacuously once the bug is fixed. Fix: await a deterministic tick via a web-first signal (e.g. blur the field and `expect(...).toBeVisible()` on the next control) before the final check. Do not add a timeout.
4. `tests/e2e/auth/tc-19...:26-31` (Q4): the plan (step 2) says "fill, blur, error visible"; the test must submit an otherwise empty form to make the error appear. That deviation is documented only in a code comment. Fix: update the TC-19 step in `specs/auth.md`. `getByText('Password must be', { exact: false })` is acceptable for now (no data-test exists; recorded rule is "locate by its text"), but it is brittle if the fix rewords the message (e.g. "Use at least 8 characters") and it is not scoped. Fix: expose `registerPage.passwordError` scoped to `register-form`, matching `/password/i` + `/8/` instead of a lead phrase, so the test fails on the right assertion when fixed.
5. `tests/e2e/auth/tc-13...:46-47` plus fixtures: between `POST /users/register` 201 and `cleanupUsers(await userIdFor(...))`, a failure of `userIdFor` (login hiccup, 423 impossible but 5xx or a DB reset) leaves the user orphaned. Fix: allow `cleanupUsers` to take an email and resolve the id in teardown (plan: "by email lookup or by id"), and register it before the id lookup.
6. `tests/api/auth/api-12...:9-11`: if a regression makes the 7-character request return 201, that user is never deleted. Fix: register for cleanup when `status() === 201` before asserting 422. Same defensive pattern for API-11's duplicate request (409 expected, a 201 would leak).
7. `src/pages/register-page.ts:33-49` (`register()`) fills street/city/state immediately and is unused; TC-13 re-implements the form fill inline (`tc-13...:19-34`). Fix: split the page-object method into `fillCustomer()` + `fillAddressAfterLookup()` that waits for the lookup, and use it in TC-13; delete the dead method.
8. Plan `File:` lines are stale for TC-01..TC-13 and API-01..16, VR and A11Y (`tests/e2e/auth-*.spec.ts`, `tests/api/auth.spec.ts`, ...) while the real paths are `tests/*/auth/<id>-*.spec.ts`. Only TC-17/18/19 and API-17 are right. Fix: update the plan so ID to file is traceable.
9. `tests/visual/auth/vr-03...:22`: the baseline will contain "Password must be minimal 6 characters long." (PWD-MIN). When that finding is fixed, VR-03 goes red for a good reason, but nothing says so. Fix: add a comment/annotation referencing PWD-MIN.
10. `tests/e2e/auth/tc-01...:15-19` / `tc-02...:9-12`: absence assertions (`toBeHidden` on headings) pass at the first poll if the route has not rendered yet. TC-01 waits on `nav-sign-in` (part of the app shell, not of the `/admin` route), TC-02 on `nav-menu`. Fix: first wait on a signal that the guard/route ran, e.g. `page.waitForResponse` for `GET /users/me` (401 anonymous, 200 customer, observed by the triager), then assert absence. Plan also says "no element with a data-test starting nav-admin-"; the tests check only `nav-admin-dashboard`. Fix: check each of the plan's ids or a prefix selector with a comment.
